# ข้อตกลงการทำงานในโปรเจกต์นี้

## Space Garage — ระบบยานต้นแบบ (2026-10-26)
- อ่าน `SpaceGarage/README.md` ก่อนแก้ระบบยาน รายละเอียดสคริปต์ การตั้งค่า และข้อจำกัดอยู่ในไฟล์นั้น
- ใช้ XZ แบบ 3D: S +Z, W -Z, A -X, D +X หันหัวตามทิศเคลื่อนที่ คลิกซ้ายค้างยิงตามหัวปืน
- Space ค้างใช้เกจบูสต์เริ่มต้น 100 อัตราใช้ต่อวินาทีขึ้นกับ Jet ปล่อยแล้วค่อยฟื้น ไม่ใช่ระบบชาร์จ
- ชิ้นส่วน 4 ช่อง Gun / ArmorPlate / Wing / Jet ข้อมูล ScriptableObject เลือก Slot และใส่ Part Prefab ได้ สคริปต์กลางประกอบทั้ง 4 ส่วนตอนเล่น รองรับ SetLoadout จากหน้าปรับแต่งในอนาคต
- ผู้ใช้ใส่กราฟิกเอง ยังไม่ทำหน้าปรับแต่งหรือ UI; มีเมนูสร้างชุดทดลองพร้อมกระสุนทรงกลมโดยไม่แก้ซีนเดิม
- เพิ่มตัวอย่างประกอบสำเร็จตามคำขอที่ `SpaceGarage/Examples/StarterShip/StarterShip.prefab` มีรูปทรงพื้นฐานและข้อมูลครบ 4 ส่วน; ShipController ใช้ assembledParts แบบ serialized ซ่อนเพื่อถอดชิ้น preview ก่อนประกอบจริงตอน Awake ไม่สร้างซ้ำ

## UI — ใช้ของที่ผู้ใช้จัดไว้ (ยืนยัน 2026-10-24)
- งาน UI ให้ทำเฉพาะโค้ดและผูกข้อมูลกับ panel/ปุ่ม/ข้อความที่ผู้ใช้ทำไว้ ไม่สร้างหน้าตา panel, layout, กล่องสำรอง หรือ runtime UI เอง เว้นแต่ผู้ใช้สั่งให้สร้างโดยตรง ถ้ายังไม่ผูก reference ให้แจ้งช่องที่ต้องใส่ ไม่สร้างของสำรองแทน และไม่ย้าย/ปรับขนาด/ลำดับ UI ที่ผู้ใช้จัดไว้เอง


## Room — ประสิทธิภาพ (ผู้ใช้ยืนยัน 2026-10-23)
- Room เริ่มกระตุกหลังใส่แมพห้องใหม่ ผู้ใช้ให้คงภาพเดิม ปรับได้เฉพาะโค้ด/การวาดฉาก ห้ามลด render scale/ความละเอียด/คุณภาพไฟหรือเงาแทนเอง; อนุญาตภายหลังให้เอาเส้นดำออกเฉพาะรายละเอียดรอง/ส่วนถูกบังที่ไม่สำคัญ ไม่ใช่เส้นหลักทั้งห้อง
- ผู้ใช้ไม่ต้องการ Maximize On Play: ห้ามตั้งอัตโนมัติหรือเปลี่ยนเลย์เอาต์แทนเอง. วัด FPS ต้องระบุว่า Unity เป็นแอปที่มีโฟกัสจริงหรืออยู่เบื้องหลัง และแยกภาระ EditorLoop/SceneView/Animator ออกจากเกม
- RoomRenderBatcher บน root Room รวมชุดวาดเฉพาะฉากนิ่งตอนเข้า Play พร้อมชดเชย Toon outline ตามสเกลเดิม ใช้ Material สำเนาในหน่วยความจำเฉพาะรอบเล่น ไม่สร้างไฟล์ .mat; ห้ามใช้ StaticBatchingUtility.Combine ตรง ๆ โดยไม่ชดเชย เพราะเส้นขอบหายบางลง
- รายละเอียดโมเดล Read/Write, occlusion bake, ผลวัด Play Mode และข้อจำกัดอยู่ใน Room.md หัวข้อประสิทธิภาพแมพห้องใหม่ ถ้าแก้ geometry/ตำแหน่งฉากนิ่งต้อง bake occlusion ใหม่
- RoomRenderBatcher รุ่นล่าสุดรวมเฉพาะชิ้นไม่มีเส้นเป็นกลุ่มพื้นที่3หน่วยก่อน static batching; ข้อมูล mesh เดิมทั้ง FBX และ RoomLook/Mesh_*.asset ต้องอ่านได้ เก็บ tangent เดิม. รายการปิดเส้น126ชิ้นอยู่ที่ Outline Disabled Renderers บน root Room ไม่สร้างไฟล์ Material ใหม่

- อ่านไฟล์ `.md` ที่เกี่ยวข้องก่อนแก้งาน และอัปเดตเอกสารเมื่อทำเสร็จ
- แจ้งผู้ใช้ก่อนแก้ว่าจะเปลี่ยนอะไร โดยเฉพาะวิธีเปิด/ปิด UI และแอนิเมชัน ห้ามเปลี่ยนวิธีทำโดยไม่บอก
- ทุกครั้งที่ส่งงาน ให้บอกสิ่งที่แก้ ผลตรวจและข้อจำกัด รวมทั้งระบุชัดว่าผู้ใช้ต้องตั้งค่าหรือทำอะไรเพิ่มไหม ถ้าไม่ต้อง ให้บอกว่าไม่ต้อง
- สรุปงานให้เป็นรูปธรรมทุกครั้ง: ทำอะไรไป เขียนหรือแก้สคริปต์/กราฟ/ซีน/prefab ที่ไหน เพิ่มหรือลบช่องอะไร อยู่บน component/node ใด แต่ละช่องรับข้อมูลอะไร ผู้ใช้ใส่อะไรได้ และต้องลาก/กรอก/บันทึกอะไรต่อ ระบุว่าไม่มีช่องใหม่เมื่อไม่ได้เพิ่มช่อง
- เมื่อข้อกำหนดเรื่องพฤติกรรม หน้าตา หรือตำแหน่ง UI ไม่ชัด ให้ถามผู้ใช้ก่อนทำส่วนที่ขึ้นกับคำตอบ ห้ามออกแบบหรือเปลี่ยนวิธีแทนเองโดยไม่แจ้ง โดยเฉพาะการเลือกช่อง UI ใหม่ การซ่อนด้วย alpha แทนปิด GameObject และการเพิ่มแอนิเมชันทดแทนของเดิม
- ผู้ใช้เป็นผู้กำหนดการออกแบบและพฤติกรรมเกม ถ้าคำสั่งยังไม่ระบุวิธีหรือมีหลายความหมาย ต้องถามและรอคำตอบก่อนแก้ส่วนที่ขึ้นกับการตัดสินใจนั้น ห้ามเลือกพฤติกรรมใหม่เองแล้วเพียงแจ้งว่าจะทำ การแจ้งแผนไม่ใช่การอนุมัติ เช่น คำว่าให้มอนพยายามเคลื่อนที่ ไม่ได้อนุญาตให้เพิ่มการเดินวนรอบผู้เล่นเอง ห้ามขยายขอบเขตแทนผู้ใช้ (ผู้ใช้ย้ำอย่างชัดเจน 2026-10-23 หลังเกิดซ้ำหลายครั้ง)
- อย่าสรุปว่าผลบนจอใช้ได้จากเพียงคอมไพล์ผ่านหรือ reference ถูกต้อง แยกให้ชัดว่าตรวจข้อมูล ตรวจเส้นทางแสดงผล เรนเดอร์ดูภาพ หรือทดสอบ Play Mode จริงแล้วระดับใด
- การแสดงรายละเอียดหลัง AnswerChek: ปิดแผงไว้จริง แล้วเปิดหลังหลอดกลับตำแหน่งเพื่อให้แอนิเมชันเข้าเดิมทำงาน ไม่เปิดแผงค้างแล้วซ่อนด้วย alpha และไม่เพิ่มเฟดทดแทนเอง

- ก่อนสร้างหรือปรับโครงสกิล ต้องอ่าน Skill.md และเทียบสคริปต์สกิลเดิมที่ใกล้เคียง (เช่น JugOrNot/MagicCircle) รวม lifecycle, เสียง, hit/critical VFX, ตัวคูณดาเมจ และค่าสำรองทดสอบ ถ้าความหมายโครงสร้างไม่ชัดให้ถามก่อน ไม่เขียนรูปแบบใหม่เอง
- มอนสเตอร์ทุกตัวที่ทำหรือแก้ต่อไปต้องมีเส้น/สัญญาณบอกทิศหรือพื้นที่โจมตีให้ผู้เล่นอ่านได้ ใช้ระบบ EnemyAttackTelegraph เดิมตามรูปแบบการโจมตี และแจ้งตำแหน่งช่องปรับให้ผู้ใช้ (ผู้ใช้ย้ำ 2026-10-21)
- อนิเมชันโจมตีมอนทุกตัวใช้ชื่อ `Attack` ตามผู้ใช้ยืนยัน ใช้ Animator Trigger ชื่อนี้กับ controller ที่มีอยู่ ไม่ตั้งชื่อท่าใหม่เอง
- ผิวมอนทุกตัวใช้ `Toon/Toon` ของโปรเจกต์พร้อมเส้นขอบ เก็บสี/texture เดิมรวมถึงสีเงา และชดเชยความหนาเส้นตามสเกล renderer; ใช้และแก้ Material เดิมที่ผู้ใช้จัดไว้ในโฟลเดอร์มอน ไม่สร้างสำเนาเพิ่มให้รกโดยอัตโนมัติ หากพบว่า Material ใช้ร่วมจนกระทบตัวอื่นให้แจ้งก่อนตัดสินใจสร้างเพิ่ม; เอฟเฟกต์ที่พึ่ง shader เฉพาะยังใช้ shader เดิม (ปรับตามผู้ใช้ยืนยัน 2026-10-23)
- มอนทุกตัวต้องใช้ Knockback และแฟลชตัวสีขาวเมื่อโดนตีผ่าน Hit Reaction ของ Enemy.cs คลาสลูกต้องเรียก base lifecycle/พัก AI ระหว่างโดนตีและคืน Material Toon/เส้นเดิมหลังจบ ตัวที่เคลื่อนที่เองต้องรองรับ MoveHitKnockback ด้วย (ผู้ใช้ย้ำ 2026-10-21)
- การแก้สี/ความเข้ม VFX ต้องคงพฤติกรรมโคนที่ผู้ใช้ขอไว้ ไม่ลบโปรไฟล์หรือคืนกราฟทั้งชุดเอง; โคนแผ่วหมายถึงขอบนุ่ม ไม่ใช่หน้า cut ทึบ สำหรับ Cataclysm Ray ผู้ใช้เลือกช่วงขอบนุ่ม2% (ประมาณ0.8หน่วยที่Size50)
- ไฟล์ตรวจงานที่สร้างเอง เช่น สคริปต์ชั่วคราว ภาพทดลอง ผลตรวจ และ .meta ต้องลบหลังใช้เสร็จ ตรวจ reference ก่อนลบ asset และเก็บผลสำคัญไว้ในเอกสารแทนไฟล์ขยะ (ผู้ใช้ย้ำ 2026-10-22)
